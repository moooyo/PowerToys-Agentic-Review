# Automatic investigation conclusion replies

## Workflow

An authorized assignment starts a native investigation. Once its complete root report is sealed,
an enabled repository policy supplies the frozen English PR or Issue template. The Server queues
the reply, verifies the publishing GitHub identity, freezes the rendered comment, and prepares,
confirms, and publishes it without asking a person to review that report. The existing manual
action toolbar remains available for other operations.

Both reply templates start with a disclosure identifying the model, the GitHub account represented
by the automation, and the possibility of AI-generated errors. PR replies retain Conclusion,
Summary, and Findings. Issue replies use Triage result and Next steps so the reader can see the
classification and required follow-up immediately. Their short summary is incorporated into the
conclusion rather than repeated under a separate heading. A final, initially collapsed section
retains the full findings, assessment rationale, validation, complete plans, exact source scope,
limitations, and additional evidence. Its toggle is Details for PRs and Investigation details
for Issues.

Template version 4 requires exactly one of each placeholder in the corresponding order:

- PR: `{{identity}}`, `{{conclusion}}`, `{{summary}}`, `{{findings}}`, and `{{details}}`.
- Issue: `{{identity}}`, `{{conclusion}}`, `{{next_steps}}`, and `{{details}}`.

Identity must be the first nonempty content and Details must be last. The renderer owns the
disclosure and the collapsed wrapper, which uses `<details>` without an `open` attribute. The
Issue wrapper uses `<summary>Investigation details</summary>`; the PR wrapper keeps
`<summary>Details</summary>`. Earlier template versions, including versions 2 and 3, do not
authorize new publication and must be saved once using the current format. Existing frozen
comment bodies are not rewritten.

## Issue triage presentation

Bug reports use the identity phrase "conducting this automated bug triage." Feature and other
Issue classifications use "conducting this automated issue triage." Classification is taken
from the sealed assessment; the renderer does not assume every Issue is a bug.

A bug conclusion presents the assessment and a concise explanation incorporating the summary
in two or three sentences, followed by a separate Runtime reproduction field. The visible next
step is selected from the same structured assessment:

| Assessment | Visible next step |
| --- | --- |
| Confirmed bug | Suggested repairs from confirmed findings and any recorded fix plan. |
| Needs more information | The exact recorded information requests for the reporter. |
| Needs verification | Unconfirmed hypotheses and the proposed reproduction or verification plan. |
| Already fixed upstream | The recorded upstream fix and a request to verify whether it is present in the reporter's build. |
| Duplicate | The original Issue reference and a recommendation to continue its discussion. |
| Expected behavior | The expected-behavior explanation and a request for precise contrary observations, if any. |

Runtime reproduction remains an independent result: Not attempted, Reproduced, Not reproduced,
or Blocked. Not attempted represents the recorded `not_run` state. Feature and other Issue
reports omit this field. Failure to reproduce does not mean the report is not a bug. A confirmed static defect does not
claim runtime reproduction. A hypothesis remains a hypothesis, and a proposed plan does not
claim execution. Upstream fix evidence does not establish a released version. Recommendations
do not claim that labels, closure, or other repository mutations have been performed.

Feature requests retain their own assessment and follow-up: missing information, open decisions,
requirements and acceptance criteria, existing usage, alternatives, or a duplicate reference.
Other Issue classifications retain their explanation without an invented bug result. Feature
readiness does not claim implementation. An empty check collection explicitly says validation
was not run. Detailed findings, including priority and evidence, remain in Details rather than
being presented as a PR-style defect list in the Issue's main body.

### Example: a bug report that needs information

The following is an illustrative layout, not a comment sent to GitHub. Model and account names,
assessment, requests, and evidence come from the corresponding recorded data in actual replies.
The shortened Investigation details content below illustrates placement rather than a complete
sealed report.

```markdown
I'm GPT-6 Astra, conducting this automated bug triage on behalf of GitHub user `@moooyo`. This triage was generated by AI and may contain errors.

## Triage result

**Needs more information.**

The report describes a shortcut that does not trigger the expected action, but the affected version and exact reproduction steps are missing. There is not yet enough evidence to determine the cause.

**Runtime reproduction:** Not attempted.

## Next steps

Could you provide:

- Which PowerToys version is affected?
- What exact shortcut and sequence of actions trigger the failure?
- What result did you expect, and what happened instead?

<details>
<summary>Investigation details</summary>

### Validation

No validation checks were recorded in this example.

### Scope

The issue text and discussion snapshot were reviewed.

### Limitations

The reported behavior has not been reproduced.

</details>
```

## Attribution

The Worker records the CLI engine and explicitly selected model for each accepted analysis round,
separately from model-generated analysis. The Server derives the attempt and round binding,
preserves this history across recovery, and requires the sealed report context to match the
accepted checkpoint. Runtime execution receipts cannot replace or fabricate this history.
These records identify the explicit CLI selection; they do not attest to a provider's internal
routing. Multiple selected models remain visible. Unrecorded rounds or a CLI default without an
explicit model selection produce an honest unavailable-model disclosure, never an invented name.

The represented GitHub user is the publishing credential's account. The transport reads `/user`,
checks its numeric ID against deployment configuration, and supplies its login to the renderer.
This identity is independent of model text, the assignment sender, and console display names.
The frozen identity is checked again during transport preflight before publication.

## Authorization and delivery

The policy is an explicit repository grant by an account with management and comment-publication
permissions. It captures the authorizing account and policy version. Saving or enabling settings
does not create comments from earlier reports. Every new outbox entry is inserted in the report
sealing transaction and freezes the template text, policy version, and exact report reference.
No GitHub request occurs inside that transaction. The dispatcher resolves the verified publisher
asynchronously, rechecks authorization and its lease, and atomically saves the identity, rendered
body, source revision, and deterministic per-report ActionIntent request before preparation.
Once saved, that comment and identity survive retries and restarts unchanged.

Automatic publication uses an internal actor scoped to one repository and the ordinary `comment`
action only. It reuses native ActionIntent preparation, confirmation, and GitHub transport. The
current policy, current authorizing account permissions, report/payload binding, and processing
lease are checked at both durable transitions and immediately before the outbound request.
The upstream target and frozen publishing identity are independently checked by the transport.
A repository identity change disables its policy and advances its version atomically with
registration. A publisher change blocks an unsent comment instead of silently changing its
attribution.

Claims and leases prevent concurrent preparation from changing the frozen message. The native
intent's executing transition permits at most one submission. Recovery first resolves existing
terminal intents even when publication has since been disabled. Executing or unknown intents
are only reconciled with read-only requests. A bounded failure leaves an observable receipt and
does not grant another write attempt.

## Deliberate bounds

Only complete initial `pr-review` and `issue-investigate` reports are eligible. Partial analysis,
failed/cancelled work, and execution follow-ups are not posted as final conclusions. The first
delivery format is one comment per report, with 59,000 UTF-8 bytes available for rendered content.
Oversized output is explicitly blocked; findings are never truncated to fit. The renderer does
not invoke a model to shorten or invent conclusions. Templates are text with a fixed set of
required placeholders, not executable code.

The repository UI can edit both templates and inspect delivery status and frozen comments.
Enabling requires publication permission; disabling only requires repository management.
The global external-write switch and GitHub credential remain deployment controls. Automated
tests use mocked transports and isolated databases; live test writes require their own exact
approval scope under the repository instructions.
