# 结构化调查结果、完整复核 Loop 与结果驱动的操作

状态：已按本文完成 breaking refactor，并通过远端全量测试、类型检查、构建及浏览器检查。以下产品要求来自用户在 2026-09-15 提出的需求。
Server、Worker 和 Dashboard 的正式入口已切到新的 Task/Report 路径。
实际字段以 [结果契约](../../packages/contracts/src/investigation.ts) 为准，
[配套 JSON](./examples/investigation-result-v1.example.json) 已按实际 schema 生成，仍是合成示例。
验证范围与结果记录在[实施状态](../IMPLEMENTATION_STATUS.md)，不能用合成数据或旧里程碑代替新路径的真实部署验收。

## 重构原则

用户已明确允许 breaking changes，不需要兼容现有接口，也不需要 migration。
本设计直接定义目标架构，允许重写 JSON schema、API、数据库表、Worker 协议和前端状态模型。

- 不实现旧接口适配层、旧新协议并行、双写、旧结果转换或数据库迁移脚本。
- 不保留仅为旧 `ReviewRun → request → Job → RunAttempt` 调用链服务的对象层级。
- 不因旧字段、端点或 UI 组件已经存在，就把它们作为新设计的输入约束。
- 新部署和验收直接使用新 schema 初始化的数据库与新结构夹具；旧数据导入和旧任务接续不属于交付要求。
- 接口切换时，Server、Worker、Dashboard 和测试夹具按同一新协议交付；不要求旧客户端继续工作。
- 源码版本绑定、证据真实性、完整性、权限、租约 fencing 和发送幂等仍是业务正确性要求，具体实现可以重写。

文中的 `V1` 表示新协议的首个明确版本，不表示要兼容旧 PR/Issue V1/V2 契约。
新系统内的报告历史与人工处置审计属于目标业务能力，与迁移旧系统记录是两件事。

## 产品要求

PR 审查和 Bug 调查必须覆盖声明的完整范围，逐条复核所有候选问题，并最终一次交付完整报告。
不能在找到第一个有用问题、选出 top-k，或达到某个偏好的问题数量后停止。
优先级用于安排最终展示顺序，不能决定哪些问题被保留或丢弃。

对外结果使用结构化 JSON。Dashboard 根据有明确类型的事实和 Server 提供的操作上下文渲染界面，
不能通过解析自然语言来推断是否完成、操作权限、根因、复现情况或下一步操作。

设计必须区分以下概念：

- 任务执行结果与代码正确性、产品验收结果。
- 调查是否完整与运行时验证覆盖是否充分。
- 模型判断与独立观察得到的验证证据。
- 原始源码、本地补丁和已经存在的远端分支。
- 推荐操作、当前可用操作和用户已确认执行的意图。
- 静态 Issue 分诊与允许执行代码的 Bug 调查、复现。

静态分诊可以以 `needs_information` 或 `needs_verification` 结束，但不能执行仓库代码或自行推断被测源码提交。
需要执行代码的调查，必须根据明确的执行授权使用单独冻结的源码和执行计划。
两条路径都在各自声明且获准的调查范围内进行 Loop。
Feature 分析遵循相同的完整性与计划规则，但不能把产品选择包装成 Bug 问题。

## 目标架构与对象模型

以 `Task` 作为唯一业务执行对象，统一 PR 审查、Issue 调查、关联验证和后续实现。
对象关系为：`WorkItem → Task → Attempt / LoopCheckpoint → Report`。
`Plan` 保存后续工作，`ActionIntent` 保存用户准备并确认的操作；二者不能冒充已经执行的 Task。
这是数据归属关系，不要求每次请求逐层穿过全部对象。检查点属于逻辑 Task，由具体 Attempt 产生；
恢复后的新 Attempt 可以继续处理同一 Task 的候选与复核记录，报告记录所有被采用的执行来源。

| 对象 | 职责与关系 |
| --- | --- |
| `Repository` / `WorkItem` | 仓库与 PR/Issue 身份、当前状态及来源快照。 |
| `Task` | 一次明确的工作目标，冻结 `kind`、被测对象、调查范围、配置、权限与预算；通过 `parentTaskId` 关联后续工作。 |
| `Attempt` | Task 的一次执行尝试，负责租约、Worker、进程、时间、取消和终止原因；重试不创建另一个业务目标。 |
| `LoopCheckpoint` | 保存 Task 的覆盖进度、全部候选、逐条复核、已执行步骤和剩余工作；绑定产生它的 Attempt 和版本。 |
| `Report` | Task 的结构化结果；包含内容版本、完整性和全部问题。每次封存的版本不可变，部分报告与最终完整报告明确区分。 |
| `Subject` | 精确区分原始 PR base/head、Issue 内容快照、指定源码提交、本地补丁与已有远端分支。 |
| `Plan` | 已保存的调查、验证、复现、修复或实现方案，绑定父报告、Subject、前提和验收标准。 |
| `ActionIntent` | 一次待确认或已确认的操作，保存目标、操作者、精确负载及执行状态；负责幂等、发送和结果核对。 |

`Task.kind` 首批覆盖 `pr-review`、`issue-investigate`、`pr-verify`、`issue-verify`、
`reproduction-setup`、`issue-fix` 和 `feature-implement`。
Bug、Feature 以及其他 Issue 的调查都可以由 `issue-investigate` 承载，用 `assessment.kind` 区分结论。
冻结的执行策略明确调查是仅使用快照、允许检查指定源码，还是允许执行验证；模型不能自行扩大这个范围。

一个验证 Task 可以包含多个场景和检查。它们通过稳定的场景、检查和证据 ID 归属于同一报告，
不需要仅为复用旧 API 而重新建立 request/Job 层级。
需要独立调度、独立环境或独立重试的工作使用子 Task；聚合只读取精确绑定到父报告、计划和 Subject 的有效结果。
同一 PR 报告可以关联 Windows、Web 等多个验证 Task。
预期覆盖来自冻结计划，而非已创建的 Task 数量；汇总键包含计划 ID/版本、场景/检查 ID、Subject 和选定的权威执行尝试。
重试不重复计数，也不能只挑选通过结果、忽略尚未执行的必需场景，或把本地补丁结果计入原始 PR。

可以复用已经证明有效的进程管理、证据存取等内部实现，但复用以目标模型合适为前提。
旧结果 DTO、旧完成端点、旧 `override_approve` 分支和旧页面适配器可以直接删除或替换。

## 标准化对外结果

采用 `InvestigationResultV1` 作为带版本的对外联合类型。
结果直接绑定 Task、Attempt、Report 和 Subject；关联验证通过父 Task 与父 Report 建立关系。
模型输出、Worker 事实和 Server 操作上下文按各自职责组装，不再兼容旧结果包裹层。

| 字段 | 含义与权威来源 |
| --- | --- |
| `schemaVersion`, `id`, `version` | Server 分配的结果身份，以及用于区分 schema 的类型信息。 |
| `context` | 仓库、工作项、`task`、`attempt`、冻结版本、profile 与 prompt 引用、Subject 集合，以及可选的父报告引用。 |
| `outcome` | Worker/Server 确认的执行结果：`completed`、`blocked`、`failed`、`cancelled` 或 `interrupted`。 |
| `report` | 不可变报告清单、完成与复核状态、覆盖范围、限制、Loop 记录、各集合数量及摘要。Server 根据已保存的记录重新计算数量。 |
| `findings` | 按顺序排列的完整保留问题集合。逻辑上的完整 JSON 导出包含全部问题；分页 HTTP 响应使用下文说明的清单视图。 |
| `assessment` | 按类型区分的 PR、Bug、Feature 或其他 Issue 评估，并绑定被评估对象。 |
| `validation` | 计划检查与实际检查、是否必需、源码绑定和执行器结果。 |
| `verificationEvidence` | 已登记的观察记录，包含来源、溯源信息、被测对象绑定和产物引用。模型不能自行生成具有权威性的执行器证据。 |
| `diagnostics` | 具有明确类型的阻碍、失败、限制和恢复信息。 |
| `artifacts` | 有作用域约束的日志、图片、trace、补丁和报告引用；当前可用性与历史身份分开记录。 |
| `plans` | 已持久化、带版本的继续调查、验证、复现、修复或实现计划。 |
| `nextActions` | 已校验并持久化的操作建议，包含 `recommended`、前提条件，以及已保存计划或草稿的引用。 |
| `feedbackDrafts` | 与问题选择独立保存的类型化反馈草稿，可用于询问、解释和后续讨论；实际发送仍通过操作准备与确认。 |

模型返回字段更少的 `InvestigationAnalysisV1`，或大小受限的单轮 Loop 结果。
校验模型输出后，再补入 Worker 的观察记录和 Server 字段。
模型不能设置 `allowed`、声称远端分支已经存在、将证据标为已验证、选择真实发布者身份，
也不能提供任意可执行的 API URL。

`ActionContextV1` 是 Server 单独返回的当前操作上下文。
它包含准确的目标状态、操作者能力、报告与问题处置依据、推荐操作 ID、固定操作，以及各操作的检查条件。
权限和当前 SHA 不能永久冻结在模型报告中。

### 执行结果与完整性

`report` 包含：

- `delivery`：`final` 或 `checkpoint`。
- `completeness`：`complete` 或 `partial`。
- `summary`：对声明调查范围的简明评估。
- `coverage`：范围清单 ID 与摘要、纳入的调查单元、明确排除项及其原因、已完成单元和未完成单元引用。
- `recheck`：最终问题总数、针对最终版本的有效复核数量，以及待复核 ID。
- `loop`：检查点 ID、已完成轮次、已发现/确认/撤回/合并/未决候选数量、停止原因，以及配置和已消耗的预算。
- `limitations`：每项重要限制及其对结论或操作的影响。
- `collections`：各集合总数及不可变摘要。

`completed` 要求调查报告已经封存、结构有效且调查完整，
不要求结论推荐批准、不要求零缺陷，也不要求 E2E 检查全部通过。
完整分析可以得出“仍缺少报告者提供的关键信息”，也可以为未解决的假设形成已保存的验证计划。

`blocked` 表示明确的前提条件缺失阻止调查完成；`failed` 表示执行或协议失败；
`cancelled` 表示明确取消；`interrupted` 表示调查尚未完成但可能恢复，包括预算耗尽。
这些结果都保留最近一份已验证的部分问题集合和具体诊断信息。
终止时交付的部分报告可以使用 `delivery: final`，但必须保持 `completeness: partial`，不能改称 `completed`。

Task 的调度状态与 Attempt 的租约、进程状态记录运行情况。
CLI 退出码为零或结果上传成功，都不足以推出 `outcome: completed`。
执行结果的视图需要结合已接受的调查检查点和终止原因；验证检查失败可以与调查成功完成同时存在。

完整覆盖表示明确范围内的每个单元都完成了要求的工作，不表示在数学上证明不存在任何未知缺陷。
PR 范围从完整 diff 和受影响行为开始，并纳入分析中发现的调用方、依赖和测试。
不能在超时后悄悄把范围缩小为已经看过的文件。
生成文件、二进制、无法访问或明确排除的输入，都要保留可见记录及原因。

### 问题记录契约

每条问题都包含以下内容；信息未知时必须明确标记：

| 字段 | 必需内容 |
| --- | --- |
| `id`, `version`, `ordinal` | 稳定身份、当前内容版本和确定的展示顺序。 |
| `priority`, `title` | P0、P1、P2 或 P3，以及简洁、可操作的标题。 |
| `trigger` | 触发条件、相关输入和暴露问题的步骤。 |
| `impact` | 可观察影响、受影响的用户或系统，以及实际严重程度。 |
| `rootCause` | `established`、`hypothesis` 或 `unknown`，并附解释和证据引用。不能为填满字段而编造未知根因。 |
| `subjectRef` | 准确的原始版本、本地补丁或其他被评估对象。 |
| `locations` | 仓库相对路径、源码范围及版本绑定；对于 UI 和 Issue 问题，也可使用明确的非源码位置。 |
| `evidenceRefs` | 已存在且作用域一致的证据；区分静态推导、报告者描述、执行器观察和视觉观察。 |
| `confirmation` | `confirmed` 或 `hypothesis`、证据依据，以及最终内容版本的复核引用。仅有置信度不等于确认。 |
| `fixRecommendation` | 建议的修复方式、约束和可选的持久化计划引用。 |
| `feedbackDraft` | 可独立编辑的评论正文，以及可选的代码替换建议。 |

源码位置并非所有问题的必填条件：真实 Bug 或 UI 问题即使无法定位到某一行，也可能具备可操作性。
行内代码 suggestion 则必须具备有效且准确的版本、范围和原始内容摘要。
语法、范围、目标 SHA、范围重叠及负载大小都单独校验，不依赖模型置信度。

复核记录保存检查过的证据、受证据支持的简短结论、未解决问题、问题内容版本，以及确认该结论的轮次身份。
这些是可审计的工作产物，不要求披露或保存模型的私有思维链。

人工处置使用独立、带版本的事件流。
被驳回的问题不能悄悄从报告中删除；接受风险也不等于解决已经确认的 P0。
本地修复不等于当前原始 PR 版本中的缺陷已经解决。

### 分类评估联合类型

PR 评估包含 `reviewConclusion` 和 `e2eAssessment`：

- `reviewConclusion.status`：`no-blocking-findings`、`changes-requested`、`inconclusive`。
- `e2eAssessment.level`：`not_needed`、`recommended`、`required`。
- E2E 同时记录判断依据、预期场景、前提条件、已保存计划、准确源码绑定和关联验证结果。
  证据是否充分，由当前具有权威性的检查结果计算，不能仅由等级或模型措辞决定。

`no-blocking-findings` 描述已审查范围，不表示必需的运行时证据已经充分。
E2E 卡片和操作推荐单独呈现。

Bug 评估包含 `bugAssessment.status` 和 `reproduction.status`：

- Bug 状态：`confirmed`、`needs_information`、`needs_verification`、`already_fixed`、`duplicate`、`not_a_bug`。
- 复现状态：`reproduced`、`not_reproduced`、`not_run`、`blocked`。
- `confirmed` 需要有依据的缺陷判断；如果静态证据已经证明缺陷，不一定要求动态复现。
- `not_reproduced` 不等于 `not_a_bug`。
- `already_fixed` 需要明确的上游提交、PR 或发布版本及其证据。本地补丁是另一个验证对象。
- `duplicate` 需要明确的原始 Issue 和具体的重合证据。

Feature 评估包含 `featureAssessment.status`：`ready`、`needs_information`、`needs_decision`、
`already_supported`、`duplicate` 或 `not_feasible`。
`ready` 要求具有需求、可行性依据、已保存的实现计划、验收标准和前提条件，
不代表维护者已经接受需求，也不代表本地环境已经就绪。

其他 Issue 类型，包括文档、问题咨询和支持请求，保留明确的 `other_issue` 分支，并附解释和有效操作建议。
无法确定分类时，不能强行套用 Bug 或 Feature 评估。

## 内部 Loop 与最终交付

Worker 根据 Task 的执行策略，在 Attempt 的租约、截止时间、取消和进程管理约束下负责 Loop。
一次 CLI 调用可以在内部执行多个步骤，但仅在提示词中要求“认真审查”并不构成完整的 Loop 协议。

1. 冻结任务身份、原始源码或 Issue 快照、可信上下文、prompt/profile、预算和完整的初始覆盖范围清单。
2. 分析每一个待处理调查单元，追加所有候选问题。发现依赖、新假设或新增受影响行为时，明确扩充待办列表。
3. 按触发条件、证据、影响、源码归属和其他可能解释，逐条复核候选问题。
   记录 `confirmed`、`withdrawn`、`merged` 或 `unresolved`。
   合并时保留原候选 ID 和原因；不能仅因问题位于同一文件或属于宽泛的同类根因，就把不同缺陷合并。
4. 继续调查当前允许范围内的剩余问题；需要其他源码、环境或执行授权的工作，更新到相应计划中。
   未解决假设保留在报告里，不能作为已确认问题呈现。
5. 对每条保留问题的最终内容版本进行一致性检查和最终复核。
   修改问题内容后，旧复核失效；此阶段发现新候选或重要缺口时，重新加入待办列表。
6. 持久化全部报告分段、草稿、计划和操作建议。
   Server 核对范围与候选统计、最终版本复核、引用、数量和摘要，再原子封存一份报告。

当所有必需调查单元已处理、每个已知候选都有处置记录、每条保留问题都有当前有效复核，
且剩余不确定性已通过结论、限制和适当下一步明确表达时，Loop 才能结束。
最后一轮不能留下未处理的范围或候选问题，也不能采用“固定三轮就算完成”之类的捷径。

模型或 CLI 输出是具有明确类型的被动数据。
单轮结果包含检查点输入摘要、覆盖更新、候选变更、复核记录和继续执行请求，
不能改变已冻结的执行权限，也不能直接执行其中建议的操作。

时间、token、轮次、存储和进程限制仍然有上限。
触达限制时，不能通过丢弃低优先级问题来产生 `completed`。
必须保存部分报告、未处理范围和准确停止原因。
恢复前核对版本和配置一致，再从 Server 最近接受的检查点继续，必要时创建新的 attempt 和租约。
源码变化或配置不兼容时，创建关联旧结果的新调查，不能跨版本拼接结论。

预算耗尽后可以由用户显式增加额度并恢复同一 Task。
新额度只能单调增加；Server 保存旧额度、新额度、操作者、请求幂等标识和检查点引用的审计记录。
增加预算不会改变源码、范围、prompt/profile 或执行权限，也不会清空已消耗额度与已复核问题。

检查点写入使用 Attempt 的租约 fencing，并结合 CAS 版本和内容摘要。
重复提交相同内容保持幂等；同一分段身份携带不同内容时拒绝写入。
恢复依赖持久化状态重建，不能只依赖仍在运行的 CLI 会话；也不能盲目重放观察记录或已执行操作。

用户看到的是覆盖进度、复核数量和当前阶段。
内部分页或检查点不能作为连续多批 top-k 最终报告发布。
部分结果可以在明确标记的未完成结果视图或终止失败视图中查看。
即使后续轮次失败，检查点中已验证且适用于当前源码的 P0 仍参与 Approve 检查；
未经校验的模型输出片段不能新增或抹除这条禁令。

## 有界传输下的完整报告存储

完整报告不能存在 top-k 或固定问题总数上限。
不继承旧协议的 100 条问题和 2 MiB 完成响应限制；重新设计流式读取、分段上传、分页和资源预算。
单请求字节数、分页大小、单报告总字节预算根据目标工作负载确定，不将旧常量作为兼容条件。
资源仍需有界；超出预算且无法继续时，必须返回明确的部分结果，不能删减问题后宣称完成。

引入大小受限的 `InvestigationReportPartV1` 上传协议，保存问题、证据引用、覆盖信息、候选处置、草稿和计划。
每个分段携带 Task/Report/Attempt 身份、所属集合、序号范围、预期前序记录或版本、数量和摘要。
使用新协议规定的请求限制和冻结的单报告存储预算。
大体积证据正文使用有明确作用域的产物引用；大体积报告内容使用有明确类型的报告分段。

最终的 `InvestigationReportManifestV1` 记录全部有序分段、数量和规范化的逻辑内容摘要。
所有分段到齐并通过校验后，在一个事务内完成封存。
暂存分段不能被宣称为完整报告；不能为适应最终负载大小而截断，也不能悄悄只保留最高优先级的问题。

摘要计算必须避免自引用。
持久化集合分段通过报告 ID 和版本绑定父报告，不包含父报告最终才会生成的摘要。
先对规范化的持久化负载计算分段摘要，再根据固定报告头和有序分段摘要计算报告内容摘要，排除摘要字段自身。
展开后的 API 引用可以将父报告摘要作为派生元数据返回，但不能再把这些元数据或实时操作上下文纳入内容摘要计算。
schema 必须明确规定这些计算视图，不能递归地对所有展示字段求哈希。
如需完整导出文件的字节哈希，应作为单独的响应元数据提供。

逻辑上的完整导出使用 `InvestigationResultV1`，包含完整集合。
受大小限制的 Dashboard 读取则返回报告头、清单和集合分页，并使用不同的 schema 类型标识；预览不能标为完整结果。
分页和完整下载都绑定同一个报告 ID、版本和摘要。
UI 可以显示“已加载 50 / 137 条”，而 Server 策略仍评估全部 137 条问题。
如果大小限制阻止最终保存，返回部分结果和明确的恢复信息。

新系统内已经封存的报告保持不可变，以支持同一 Task 的中断、恢复和后续验证审计。
旧结果无需转换为新报告，也不要求新界面读取旧 schema；不实现历史数据回填或 migration。

## 新 API 与存储边界

API 直接围绕目标对象设计，不沿用旧端点和参数结构。以下是拟议的职责划分：

| API | 职责 |
| --- | --- |
| `POST /api/tasks` | 根据明确目标或有效保存的计划创建 Task，冻结 Subject、配置、执行策略和预算。 |
| `GET /api/tasks/:taskId` | 返回 Task 当前状态、Attempt、最新报告引用和子任务概况。 |
| `POST /api/tasks/:taskId/resume` | 根据有效检查点和一致的 Subject/配置创建恢复 Attempt。 |
| `POST /api/tasks/:taskId/cancel` | 记录取消意图，并由执行控制链确认停止与清理。 |
| `GET /api/reports/:reportId` | 返回指定版本的报告头、清单、评估与各集合引用。 |
| `GET /api/reports/:reportId/findings` | 对同一封存版本游标分页，返回完整总数和页面范围。 |
| `GET /api/reports/:reportId/export` | 流式导出完整 JSON，不把第一页或预览包装为完整报告。 |
| `GET /api/work-items/:workItemId/action-context` | 根据当前账号、目标和可选报告基准返回固定操作、有效建议与检查条件。 |
| `POST /api/action-intents` | 根据操作注册表创建精确、可预览的操作意图，绑定所选问题、草稿、计划与目标。 |
| `POST /api/action-intents/:intentId/confirm` | 校验预览绑定和当前权限，确认该操作意图；重放相同确认不能重复执行。 |
| `GET /api/action-intents/:intentId` | 展示执行或发送结果，以及不确定状态的核对进度。 |

Task 创建和操作意图写入都使用明确的幂等标识与请求内容绑定；改变目标或负载意味着新的意图。
创建 Task 的直接入口与由 ActionIntent 派发的入口共用权限、计划、Subject 和预算校验，不能形成绕过路径。
固定操作可以没有报告基准；报告衍生操作必须提供精确的报告版本和内容摘要。

Worker 通信协议独立定义领取 Task、租约续期、检查点写入、报告分段上传和最终封存。
所有写入绑定当前 Task、Attempt、租约及内容版本，不能从客户端提交的任意 ID 推断权限。
用户 API 和 Worker API 使用各自的身份及权限，不混用执行凭据。

数据库按目标关系直接定义 `tasks`、`attempts`、`loop_checkpoints`、`report_parts`、`reports`、
`findings`、`finding_events`、`plans`、`evidence_assets` 和 `action_intents` 等表，配套全新初始化 DDL。
表的最终拆分服从事务边界和查询需求；不新增旧新数据映射表、不双写，也不维护兼容查询。

## PR 推荐与操作权限

使用三个独立的派生视图：

1. `recommendation`：建议的下一项活动，根据完整报告中的事实、问题、验证覆盖情况以及已有效保存的操作生成。
2. `hardContentBlockers`：按用户要求的规则，阻止人工 Approve 的问题。
3. `actionGuards`：当前操作者权限、目标状态、精确 SHA、请求版本、适用时的报告/处置记录绑定，以及尚未确认结果的先前发送。

Approve 的内容硬阻仅限于同时满足以下条件的 P0：已确认、未解决、适用于当前原始 PR 版本，并且有经过校验的问题/复核记录支持。
P1、缺少必需的 E2E、分析不完整以及执行失败，都是建议的输入，不构成禁止人工 Approve 的额外内容规则。
所有产生 GitHub APPROVE 的路径都适用这条 P0 规则；任何覆盖操作都不能绕过它。

| 结果事实 | 默认建议 | 人工 Approve 的内容规则 |
| --- | --- | --- |
| 当前原始版本存在已确认且未解决的 P0。 | 处理问题；准备评论、代码建议或 Request changes。 | 禁止。 |
| 不存在上述 P0，但有未解决的 P1。 | 先反馈并修复，再批准。 | 允许。 |
| 无 P0/P1；E2E 不需要或仅为建议。 | Approve；可选择对 P2/P3 提供反馈。 | 允许。 |
| 无 P0/P1；必需的 E2E 证据不足。 | 准备关联验证或前置工作。 | 允许。 |
| 无 P0/P1；必需的 E2E 已有充分验证。 | Approve；提供现有验证结果。 | 允许。 |
| 分析不完整、执行失败或报告无效。 | 检查诊断/证据，并恢复或重新运行。 | 允许，除非另有经过校验、适用于当前版本的 P0。 |

以上是内容规则，不保证 GitHub 或当前操作者允许执行操作。权限、目标状态、当前 SHA 和发送状态仍必须检查。
用户选择与建议相反的人工批准时，应记录当时展示的条件与操作意图；这不会改写失败检查，也不代表验证成功。
新模型只保留语义明确的 Approve 操作，不提供兼容旧行为的 `override_approve`。
用户在 P1/E2E 情况下自主批准，使用普通批准所需权限，并记录当时的推荐差异。

固定 PR 工具栏包含 Comment、Approve、代码建议评论、Request changes、Close、Merge 和 Trigger CI。
这些入口独立于模型输出。不支持或当前不可用的操作应显示具体原因。
Merge 和 CI 各自具有类型明确的目标、参数、权限与执行前检查；不能从 Approve 或模型提供的 URL 推导这些内容。
本设计不隐含添加针对 P0 的专用 Merge 规则。

固定 Issue 操作包括 Comment 和 Close。即使报告缺失或无效，用户仍可针对独立核实过的当前目标准备这些操作。
此类人工操作使用目标/操作者/状态绑定，不得借用无效的问题、草稿或报告摘要。
由报告产生的操作还要绑定所选报告、计划、问题和草稿。
两条路径都不能绕过尚未确认结果的先前发送。

准备与执行应分别持久化。发送前展示精确目标、操作者、载荷和来源；发送时重新检查当前授权。
结果不确定的 POST 应进入发送状态未知、需要核对的状态，不能自动重发。
如果端点不提供与 GitHub 的原子事务，确认绑定就不能声称具备这种原子性。

### 问题选择与反馈

- 有效代码建议默认选中；用户可以取消选择。假设、无效范围、过期建议以及仅绑定本地补丁的建议，不会自动作为原始 PR 的代码替换内容。
- 选中的有效建议用于准备代码建议评论。选中的纯文本问题用于准备普通评论。混合选择会同时准备两者，且只包含选中的问题及其已明确审阅的草稿。
- 代码建议是一种反馈格式；Request changes 是一种审查操作。选择内容或使用建议语法，都不会自动选择 Request changes。
- UI 将 `explicitAction` 与选中的问题 ID 分开记录。没有显式操作选择时，选中的反馈决定准备哪种操作；清空全部选择后恢复审查建议。用户明确选择的操作应予保留。
- 选择状态与草稿编辑属于用户状态。新报告版本或 SHA 变化会使已准备的载荷失效，并要求重新校验；不能静默重新定位建议。
- 替换范围重叠属于准备冲突。大量选中反馈可能需要拆成多个经过明确预览的载荷，但调查报告仍是一份完整报告，任何选中的问题都不能在没有说明的情况下消失。

## 已保存计划与有效后续操作

计划包含 ID/版本/摘要、类型、目标、对象绑定、前置条件、结构化步骤、预期观察结果或验收标准，以及报告来源。
分析请求不能静默授权执行计划。模型生成的计划只有经过 schema 校验并持久化后，才能用于后续操作。

每个 `nextActions` 条目包含 ID、白名单中的操作、可选任务类型、标签、原因、`recommended`、已持久化的计划/草稿/验证引用、精确对象，以及显式前置条件引用。
Server 将建议有效性与当前执行就绪状态分开记录。
操作的前置条件尚未满足时，可以说明缺少什么；引用无效或缺失时，不能渲染为可执行的任务按钮。

操作上下文分别返回 `canPrepare` 和 `readyToExecute`。
有效计划所需的源码 SHA 或环境信息可以先在准备表单中补充；确认执行时仍重新核对全部真实前提。
可信执行配置中已经确认的前提按精确计划独立读取，不能让不同计划复用同一前提 ID 时互相借用确认，
也不能接受模型或客户端自报“已经满足”。

模型不能向通用 UI 执行器提供 shell 命令、任意 API 方法、HTML 组件或可执行 URL。
带版本的操作注册表定义输入 schema、准备界面、权限、执行前检查、发送和结果导航。
未来或尚未支持的操作类型可以保留可读建议，但不能执行。

### 关联 PR 验证

`reviews.verify` 是操作类型，通过统一的 ActionIntent 准备和确认接口创建 `pr-verify` 任务，
不是名为 `reviews.verify` 的独立 HTTP 端点。
它引用父报告/版本/摘要、已保存的 E2E 计划、相关场景，以及精确的 PR base/head 版本。
它只创建所选验证工作，不重复完整 PR 审查。

与父报告、计划和 Subject 精确匹配的关联结果会更新 Server 当前的建议视图，原报告则保持不可变。
必需检查、场景覆盖、证据完整性、源码身份和结果时效性共同决定证据是否充分。
已有充分证据时，推荐 `view-validation`，而不是再次执行。
源码变化需要新的绑定和明确准备；旧 SHA 的通过结果不能满足当前 SHA 的 E2E 要求。
本地补丁上的验证应单独展示。

### Feature 操作

| `featureAssessment.status` | 报告必需内容 | 仅在引用已有效保存时提出的后续操作 |
| --- | --- | --- |
| `ready` | 需求、可行性证据、实施计划、验收标准、前置条件。 | 通过 `start-task` 创建 `feature-implement`。 |
| `needs_information` | 缺失事实、需要这些事实的原因，以及询问草稿。 | 通过 `comment` 发送询问。 |
| `needs_decision` | 待决策事项、备选方案、取舍、讨论草稿。 | 通过 `comment` 发起讨论。 |
| `already_supported` | 现有能力、适用条件、用法、证据。 | 通过 `comment` 提供使用指引。 |
| `duplicate` | 原 Issue、重叠部分、差异及重复证据。 | `close-as-duplicate`，或通过 `comment` 建立关联。 |
| `not_feasible` | 约束、调查证据、解释、替代方案。 | 通过 `comment` 提供解释。 |

### Bug 操作

| `bugAssessment.status` | 报告必需内容 | 仅在引用已有效保存时提出的后续操作 |
| --- | --- | --- |
| `confirmed` | 缺陷、影响、有证据支持的根因或明确保留的不确定性、证据、修复建议。 | 已保存可行计划时，通过 `start-task` 创建 `issue-fix`；也可以 `comment`。 |
| `needs_information` | 只有报告者能够补充的缺失事实，以及询问草稿。 | 通过 `comment` 发送询问。 |
| `needs_verification` | 假设、具体实验、预期观察结果、前置条件。 | 通过 `start-task` 创建 `reproduction-setup` 或 `issue-verify`。 |
| `already_fixed` | 上游 PR/commit/release 及支持证据。 | 解释性的 `comment`，可选择 Close。 |
| `duplicate` | 原 Issue 及同一问题的证据。 | `close-as-duplicate`，或通过 `comment` 建立关联。 |
| `not_a_bug` | 预期行为、设计/配置证据，以及解决指引。 | 解释性的 `comment`，可选择 Close。 |

状态用于解释建议，不会直接生成可执行按钮。
建议的任务类型需要操作注册表和执行能力明确支持。
如果缺少这些支持，应展示已保存计划和缺失能力，不能伪称任务成功。

实施结果可以提供查看变更和进一步验证的操作。
只有具名远端分支已经存在、SHA 已核实，并且明确绑定 repository/base/head 时，才能准备 `create-pr`。
该操作绝不会隐式 commit 或 push。

## Dashboard 组成

Dashboard 直接消费新的 Task、Report 和 ActionContext API，按目标产品流程重组页面与组件。
Material UI 可继续作为组件库，但旧路由、页面结构、适配器和状态模型均可替换，不增加兼容桥。
引入类型明确的视图模型构建器，避免各组件直接解释原始模型 JSON。

| UI 区域 | 输入与行为 |
| --- | --- |
| 执行结果与报告头部 | 分开展示执行结果、完整性、复核状态、当前/历史源码、覆盖情况和限制。 |
| 评估卡片 | 根据联合类型的判别字段，选择 PR 审查/E2E、Bug/复现、Feature 或其他 Issue 的渲染器。 |
| 问题列表/详情 | 完整总数、已加载数量、P0-P3 排序、确认状态与人工处置、触发条件/影响/根因/证据/修复/草稿。支持独立选择与草稿编辑。 |
| 验证与证据 | 精确的原始源码/本地补丁对象、实际检查结果、未满足的前置条件、可用日志/图片/trace、关联验证报告。 |
| 计划与建议操作 | 仅展示已持久化的有效操作、`recommended` 标记、缺失的前置条件、计划查看和类型明确的准备表单。 |
| 固定操作工具栏 | 根据 Server 当前能力提供 PR 或 Issue 操作，独立于报告是否成功及其分类。 |
| 诊断与历史 | 部分报告的覆盖情况、中断工作、错误、检查点/执行尝试历史和恢复导航。 |

主按钮是 UI 偏好，不是权限判断。
它依次遵循用户显式选择、选中反馈、Server 首选的有效建议。
如果没有可执行建议，应使用只读查看入口。
固定工具栏仍然保留，并对每项不可执行操作显示具体原因。

证据过期会改变当前可用性与建议上下文，但不会改写历史结论。
未知 schema 变体或无效结果应显示诊断结果视图；固定操作则加载其独立的当前目标上下文。

## 实施阶段与验证

1. **确定目标契约：**直接定义 Task、Attempt、Report、Subject、Plan、ActionIntent、ActionContext 和 Loop 消息 schema；实现 PR 推荐与操作权限真值表，并制作新结构的 PR/Bug/Feature 夹具。
2. **实现新存储与 API：**按目标模型创建初始化 DDL、查询与事务；实现检查点、报告分段、封存、完整分页和导出。无需旧表映射、双写、回填或迁移脚本。
3. **重构 Worker：**采用新的 Task/Attempt 协议和 Loop 协调器，实现全量候选处理、最终版本复核、中断与恢复，并同步重写提示词和结构化输出校验。
4. **实现操作策略与处理器：**以独立 ActionIntent 实现推荐、固定操作、精确预览与确认；统一 Approve 规则，并为关联验证、反馈、Close、Merge、Trigger CI、重复 Issue 关闭及实施任务提供各自的类型化处理器。
5. **重构 Dashboard：**直接使用新 API，实现结果页、分类评估、完整问题选择、证据与保存计划面板、独立固定操作栏；删除旧结果适配和不再使用的状态模型。
6. **整体切换与验收：**Server、Worker、Dashboard 和夹具按同一新契约联调，在新初始化的测试数据库上验证，然后替换旧调用链、类型、端点及失效测试。旧新版本不要求同时运行，也不引入兼容性占位代码。

以上是开发顺序，不是为了在线兼容而进行的分阶段迁移。
过程中的代码可以使用未完成的新接口；交付时要求整个新路径闭环，不能靠旧路径兜底。

必需验证场景：

- 使用跨越多个分页、超过新协议单消息大小的大报告；完整保存、计数、分页和导出，不遗漏内容，也不产生第二份面向用户的 top-k 报告。改变分页或分段大小不能改变最终问题集合。
- 首个已加载页面之外的 P0 仍阻止 Approve；取消选择不影响该规则。
- 最终复核中发现的新候选，在处理完成前阻止报告完成。
- 修改问题会使旧复核失效；重复/撤回候选仍被完整记录。源码变化后，不能把旧检查点当作当前工作继续使用。
- 中断、取消、格式错误的输出和存储耗尽，都保留经过校验的部分问题与恢复详情。部分运行不能声称完整覆盖。
- P1、缺少必需 E2E 和分析不完整会改变建议，但不会添加额外的人工 Approve 内容限制。当前已确认且未解决的 P0 不可绕过。
- 无效报告不能提供可用于操作的问题，但在当前目标/操作者状态有效时，仍可独立准备固定操作。
- 仅有效建议默认选中；混合反馈准确包含所选问题；只有用户未显式选择操作时，清空选择才恢复默认建议。
- Bug/Feature 状态本身绝不会创建任务。缺少已保存计划、绑定过期、能力未知和前置条件未满足，都应准确展示。
- 关联验证保留父任务范围/SHA，不启动另一轮完整审查。证据已充分时优先导航到结果；本地补丁验证成功不能证明原始版本通过，也不能证明上游已修复。
- 发送状态未知时，先核对再进行任何可能重复的写入。所有预览/发送防护条件均独立于模型建议重新检查。
- 验证新初始化数据库可以独立承载全流程，客户端、Worker、DTO、路由和策略不存在对旧协议的隐式依赖；无需验证旧数据升级或旧客户端兼容。

除非用户明确授权当前任务进行本地验证，否则实施测试与验证均在 `ssh test-env` 上运行。
自动化测试使用隔离数据，并模拟 GitHub 写入。
真实 PR/Issue 变更需要用户明确授权目标、操作、载荷与执行范围。
本设计请求不授权任何此类变更。

UI 场景是把通用执行器落实成可以重复运行的实际操作用例。下面是说明含义的假设用例，

4. 保存提交身份、每步操作、预期与实际结果、截图、日志和必要的配置差异。
5. 结束本次启动的进程，恢复测试配置并释放占用，使下一次运行能从同样的初始条件开始。
